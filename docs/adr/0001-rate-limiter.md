# ADR-0001: Rate limiter는 Bucket4j 인메모리 필터로 구현한다

- 상태: 채택 (구현 중, 이슈 #45)
- 날짜: 2026-11-26

## 배경

관리자 로그인, 소셜 로그인, 토큰 갱신처럼 인증 없이 열려 있는 엔드포인트는 대입 공격과 과호출에 그대로 노출되어 있다. 문의 접수(#175)와 LLM 판정 API도 비용과 스팸 때문에 제한이 필요하다. 현재 인스턴스는 1대이고 Redis는 없다.

## 후보와 검토

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Resilience4j `RateLimiter` | 이미 의존성이 있다 | 이름 하나당 한도 하나라 IP나 사용자별 제한을 직접 레지스트리로 만들어야 한다. 어노테이션은 AOP가 필요하고 전역 한도만 가능하다 | 처음 선택했다가 기각 |
| Bucket4j 인메모리 | 키별 버킷이 자연스럽다. 널리 쓰인다. 나중에 Redis나 JDBC 백엔드로 옮기는 길이 있다 | 재시작하면 초기화되고 인스턴스 간 공유가 안 된다 | 채택 |
| Redis 기반 | 여러 인스턴스에서 공유된다 | 지금 Redis가 없고 이것 때문에 인프라를 늘리기엔 이르다 | 기각 |
| Cloudflare 엣지 규칙 | 앱에 닿기 전에 막는다 | 무료 플랜은 규칙 수와 기능이 제한적이라 이것만으로는 부족하다 | 보완용으로 병행 |
| `@RateLimiter` 어노테이션 또는 AOP | 컨트롤러에 선언하면 읽기 쉽다 | 필터, 인증, 요청 파싱이 끝난 뒤에 실행되고 요청 객체에서 IP를 꺼내기 불편하다 | 기각 |

처음에는 Redis가 없다는 이유로 Resilience4j를 골랐다. 구현을 설계하면서 키별 제한이 핵심인데 Resilience4j는 이를 직접 만들어야 한다는 점, 이슈 원문도 Bucket4j였다는 점, 확장 경로가 더 좋다는 점 때문에 Bucket4j로 바꿨다. Resilience4j는 circuit breaker 용도로 그대로 쓴다.

## 결정

- Bucket4j(`bucket4j_jdk17-core`)를 인메모리로 쓰고, 서블릿 필터(`RateLimitFilter`)에서 제한한다. Spring Security 체인에서 `JwtAuthenticationFilter` 뒤에 둔다. 로그인 정보가 채워져야 사용자 키를 쓸 수 있기 때문이다.
- 정책은 `application.yml`의 `rate-limit.policies`로 관리한다. 정책마다 경로 패턴, 키 종류(IP 또는 USER), 한도, 주기가 있고 정책별로 버킷을 따로 센다.
- 키는 로그인 전 엔드포인트는 IP, 로그인 후 엔드포인트는 사용자 ID를 쓴다. USER 정책이라도 로그인하지 않았으면 IP로 센다.
- 버킷은 Caffeine 캐시에 두고 한 주기 동안 접근이 없으면 지운다. 한 주기가 지나면 버킷은 어차피 가득 차 있어서 지워도 동작이 같다. 정책당 키는 10만 개로 상한을 둔다.
- 토큰은 조금씩 채워지는 방식(greedy)이다. 경계 시점에 요청이 몰리는 문제를 줄인다.
- 한도를 넘으면 필터가 직접 429, `Retry-After` 헤더, 기존 에러 형식(`COMMON429_1`)으로 응답하고 끝낸다. 예외를 던지지 않으므로 `@RestControllerAdvice`와 Sentry를 거치지 않는다. 필터에서 던진 예외는 advice에 닿지 않는다.
- 거절될 때만 정책 이름과 IP를 WARN 로그로 남기고, IP는 끝자리를 가린다.
- 관리자 로그인의 기본값은 10분에 5회이고 환경변수(`RATE_LIMIT_ADMIN_LOGIN_LIMIT`, `RATE_LIMIT_ADMIN_LOGIN_PERIOD`)로 바꾼다. 소셜 로그인과 토큰 갱신(`auth-token`)은 분당 20회로 두었고 실제 트래픽을 본 뒤 조정할 임시값이다. `RATE_LIMIT_ENABLED=false`로 전체를 끌 수 있다.

## 클라이언트 IP

앱에 forward 헤더 설정이 없어서 `request.remoteAddr`는 프록시의 IP일 수 있다. 그러면 모든 사용자가 한 IP로 묶인다. 그래서 `RATE_LIMIT_CLIENT_IP_HEADER`로 헤더 이름을 받고, 헤더가 쉼표로 이어져 있으면 프록시가 마지막에 붙인 값만 쓴다. 앞쪽 값은 클라이언트가 위조할 수 있다.

Cloudflare를 쓰고 있어서 `CF-Connecting-IP`를 쓸 계획이다. 다만 Railway 기본 도메인으로 직접 접속하면 Cloudflare를 거치지 않아 이 헤더를 위조할 수 있다. 이를 막기 위해 `RATE_LIMIT_TRUSTED_PROXIES`(IP 또는 CIDR 목록)를 두었다. 목록이 있으면 접속한 상대(`remoteAddr`)가 목록에 있을 때만 헤더를 믿고, 아니면 헤더를 무시한다. 헤더 이름을 지정했는데 이 목록이 비어 있으면 모든 상대를 믿게 되어 헤더 위조를 막을 수 없으므로, 앱이 시작할 때 실패하도록 했다. 헤더를 쓰려면 프록시 대역을 먼저 알아내야 한다. Cloudflare나 Railway 프록시의 실제 대역은 아직 확인하지 못했다.

이 헤더가 실제로 어떻게 들어오는지는 staging에서 확인한 뒤에 정한다. 그 전에 prod에서 IP 기준 제한이 켜지지 않도록 `application-prod.yml`의 `rate-limit.enabled` 기본값을 `false`로 두었고, 확인이 끝나면 `RATE_LIMIT_ENABLED=true`로 켠다. 기본 설정(local, staging)은 켜져 있다.

## 경로 매칭과 설정 검증

- 정책 경로 매칭은 Spring MVC가 라우팅하는 경로와 같은 기준으로 한다. `UrlPathHelper`로 퍼센트 인코딩을 풀고 세미콜론 뒤를 제거한 경로를 쓰므로 `/admin/%6cogin` 같은 우회가 통하지 않는다.
- 활성화된 정책의 한도와 주기가 0 이하이거나 이름이 중복되면 앱이 시작할 때 실패한다. 환경변수 오입력이 첫 요청에서야 오류로 드러나는 것을 막기 위해서다.

## 결과와 한계

- 서버를 재시작하면 카운트가 초기화된다.
- 인스턴스를 늘리면 한도가 인스턴스 수만큼 느슨해진다. 그때는 Bucket4j의 Redis나 JDBC 백엔드로 옮기거나 Cloudflare 규칙을 강화한다.
- IP를 여러 개 쓰는 공격자는 IP마다 한도가 따로라서 이 방식으로 막지 못한다. 시크릿 강도와 Cloudflare 앞단 방어로 보완한다.
- 문의 접수와 LLM 판정 정책은 해당 경로가 확정된 뒤에 추가한다.
- 4xx 대량 발생은 Sentry가 아니라 메트릭 기반 알림으로 본다(#176). 429가 얼마나 나는지는 거절 로그로 확인한다.
- 단위 테스트는 버킷, IP 추출, 필터 흐름을 다룬다. 실제 서버에서의 필터 순서 확인과 토큰이 시간이 지나 다시 쌓이는 동작은 자동 테스트에 없다.
