# 장애 대응 런북

## 1. 문서 목적

이 문서는 운영 중 장애가 발생했을 때 **확인 순서 → 조치 → 롤백 판단 → 사후 기록**을 빠르게 따라갈 수 있도록 정리한다.
장애 상황에서 판단을 새로 하지 않고 이 문서 하나만 보고 움직이는 것을 목표로 한다.

- 운영 플랫폼: Railway (`Dockerfile` 단일 배포)
- 애플리케이션: Spring Boot (Kotlin), 프로필 `prod` / `staging`
- DB: PostgreSQL (Railway 관리형)
- 헬스체크: `/actuator/health`

### 모니터링 도구 맵

| 환경 | 주 관측 도구 | 역할 |
|---|---|---|
| 공통 | **Sentry** | 애플리케이션 에러/예외 추적, 스택트레이스 |
| **staging** | **BetterStack** | 업타임 모니터링, 로그 수집, 알림·온콜, 상태 페이지 |
| **prod** | **Grafana** | 메트릭 대시보드, 임계값 기반 알림 |
| 공통 | Railway Logs | 배포/기동/런타임 로그 (플랫폼 원본 로그) |

> 원칙: **어느 환경이든 "증상 확인은 헬스체크 → 해당 환경 관측 도구 → Railway Logs" 순서**로 좁혀 들어간다.
> staging에서 먼저 잡아 prod로 나가지 않게 하는 것이 BetterStack의 1차 목적이다.

관련 문서: [배포/운영 전략](deployment.md), [기술 스택](tech-stack.md)

## 2. 공통 진입 절차 (모든 장애 공통)

어떤 장애든 아래 순서로 먼저 상태를 파악한다.

1. **증상 확인**: 어떤 요청/화면이 실패하는가, 언제부터인가, 전체인가 일부인가
2. **헬스체크**: `GET /actuator/health` → `UP` / `DOWN` 확인
3. **최근 변경 확인**: 마지막 배포 시각과 커밋 (`main` 최신 커밋 vs 장애 시작 시각)
4. **관측 도구 확인** (환경별):
   - **staging**: BetterStack 업타임/알림 상태, 로그 스트림 확인
   - **prod**: Grafana 대시보드에서 에러율·지연·리소스 메트릭 확인
   - **공통**: Sentry 이슈 급증 여부, Railway Runtime Logs 스택트레이스
5. **범위 판단**: 특정 API만인지, 전체 5xx인지, DB 계열인지 분류 → 아래 유형별 절차로 이동

> 판단 기준: **"직전 배포 직후 시작된 장애"면 원인 후보 1순위는 방금 배포**다. 원인 분석보다 롤백을 먼저 검토한다(§9).

## 3. 장애 판단 기준 (심각도)

| 등급 | 기준 | 예시 | 대응 속도 |
|---|---|---|---|
| **P1 (치명)** | 전체 서비스 불가, 로그인/핵심 API 전면 실패 | 서버 기동 실패, DB 연결 전면 실패, 전체 5xx | 즉시 대응, 롤백 우선 검토 |
| **P2 (심각)** | 일부 기능 불가 또는 성능 심각 저하 | 특정 도메인 API 5xx, 응답 지연 급증 | 신속 대응, 원인 파악 병행 |
| **P3 (경미)** | 사용자 영향 제한적, 우회 가능 | 간헐적 오류, 비핵심 API 실패 | 정규 시간 내 대응 |

판단이 애매하면 **한 단계 높게** 잡고 시작한다.

**알림 설계 원칙**: 모든 이벤트를 같은 강도로 알리면 결국 아무도 보지 않게 된다. 심각도별로 채널·강도를 분리한다.

| 등급 | staging (BetterStack) | prod (Grafana) |
|---|---|---|
| P1 | 즉시 온콜 알림(전화/푸시) | 즉시 알림 + 대시보드 확인 |
| P2 | 채널 알림 | 임계값 알림 |
| P3 | 로그 집계로 주기 확인 | 대시보드에서 추세만 관찰 |

> P3 수준 알림은 실시간 푸시보다 **주기적 집계**로 모아 보는 편이 낫다(알림 피로 방지).

## 4. 배포 실패 대응

**증상**: Railway 배포가 실패 상태, 새 버전이 활성화되지 않음.

확인 순서:
1. Railway **Deployment Logs** 확인 → 빌드 단계 실패인지 기동 단계 실패인지 구분
   - 빌드 단계: Gradle / Docker build 에러
   - 기동 단계: 컨테이너는 떴으나 헬스체크 미통과 → §5로 이동
2. 직전 커밋 diff 확인 (`build.gradle.kts`, `Dockerfile`, 환경변수 관련 변경)
3. GitHub Actions PR 검증(`./gradlew build`, `./gradlew test`)이 통과했는지 확인

조치:
- 빌드 실패: 로컬에서 `./gradlew build` 재현 → 원인 수정 후 재배포
- 배포는 실패했지만 **이전 버전이 살아있으면 서비스 영향 없음** → 침착하게 원인 수정 우선
- 이전 버전도 영향받는 상황이면 §9 롤백 기준 적용

---

## 5. 서버 기동 실패 대응

**증상**: 배포는 되었으나 컨테이너가 기동 후 바로 종료되거나 `/actuator/health`가 `200`을 반환하지 않아 활성화되지 않음.

확인 순서:
1. Railway Runtime Logs에서 **기동 로그 마지막 줄** 확인 (스택트레이스 최상단이 원인)
   - staging: BetterStack 로그 스트림에서도 동일 확인 가능
2. 대표 원인 후보:
   - DB 연결 실패 (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`) → §7
   - 필수 환경변수 누락 (JWT 시크릿, `SENTRY_DSN` 등)
   - `PORT` 바인딩 불일치 (`${PORT:8080}` 유지 확인)
   - Bean 초기화 실패 / 마이그레이션·`ddl-auto` 충돌
3. Healthcheck **timeout** 때문에 오탐 실패로 표기된 것은 아닌지 확인 (기동이 느린 경우 timeout부터 점검)

조치:
- 환경변수 문제: Railway Variables 수정 후 재배포 (시크릿은 절대 Git에 넣지 않음)
- 코드 문제: §9 롤백으로 이전 정상 버전 복구 후, 원인 수정
- 기동 지연이 원인이면 Healthcheck Timeout을 먼저 상향(기본 300초 기준)

## 6. 5xx 급증 대응

**증상**: `/actuator/health`는 `UP`이지만 특정/전체 API가 5xx를 반환, Sentry 에러 급증.

확인 순서:
1. Sentry에서 **에러 종류 상위 1~2개** 확인 (같은 예외가 몰리는지)
2. 에러율 추이 확인: **prod는 Grafana 대시보드**, **staging은 BetterStack**에서 급증 구간 파악
3. 특정 엔드포인트 집중인지, 전체인지 범위 확인
4. 직전 배포와의 상관관계 확인 (배포 직후 시작이면 코드 회귀 의심)
5. DB 계열 예외(`SQLException`, connection pool 고갈)면 §7로 이동

조치:
- 특정 배포 회귀로 판단되면 §9 롤백
- 외부 의존성(외부 API) 문제면 해당 호출 구간 격리/타임아웃 확인
- connection pool 고갈이면 §7 및 §8 병행

---

## 7. DB 연결 실패 대응

**증상**: 기동 실패 또는 런타임 중 DB 연결 오류, `health`의 `db` 컴포넌트 `DOWN`.

확인 순서:
1. Railway PostgreSQL 서비스 상태 확인 (DB 인스턴스 자체가 살아있는가)
2. 연결 변수 확인: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`
3. Connection pool 고갈 여부 확인 (동시 요청 급증 / 커넥션 누수)
4. 최근 스키마 변경 / `ddl-auto` 설정 변경 여부 확인

조치:
- DB 인스턴스 다운: Railway에서 DB 서비스 재시작/복구
- 변수 문제: Railway Variables 수정 후 재배포
- pool 고갈: 원인 쿼리/누수 지점 파악, 필요 시 pool size 조정 후 재배포
- 애플리케이션은 살아있고 DB만 일시 불가면, 복구 후 자동 재연결 여부를 로그로 확인

---

## 8. 응답 지연 대응

**증상**: 5xx는 아니지만 응답 시간이 눈에 띄게 증가, 타임아웃 발생.

확인 순서:
1. 전체 지연인지 특정 API 지연인지 구분
2. **prod: Grafana 대시보드**에서 응답 지연(p95/p99)·리소스(메모리/CPU) 메트릭 확인 → 포화 구간 파악
3. Railway 리소스 포화 여부 확인 (Grafana 지표와 교차 확인)
4. DB 슬로우 쿼리 / connection pool 대기 여부 확인 (§7 연계)
5. Serverless(App Sleeping) 상태에서 첫 요청 cold start인지 확인 → 운영 API는 `Off` 권장
6. 외부 API 호출 지연 여부 확인

조치:
- 리소스 포화: 인스턴스 스펙/Replicas 조정 검토
- 슬로우 쿼리: 쿼리/인덱스 점검
- cold start: Serverless `Off` 확인
- 특정 배포 이후 지연이면 §9 롤백 검토

## 9. 롤백 기준

**롤백을 즉시 검토하는 조건 (아래 중 하나라도 해당):**
- 직전 배포 직후 P1/P2 장애 발생
- 5xx가 급증하고 원인 파악에 시간이 걸릴 것으로 판단됨
- 서버 기동 실패로 신버전이 활성화되지 못함
- 사용자 영향이 계속 확대되는 상황

**롤백보다 수정 우선을 검토하는 경우:**
- 이전 버전도 동일하게 영향받는 장애(코드가 아닌 DB/인프라 원인)
- 데이터 마이그레이션이 이미 반영되어 단순 롤백 시 데이터 정합성 문제가 생기는 경우

**롤백 방법 (Railway):**
1. Railway 대시보드 → Deployments → 마지막 정상 배포 선택 → **Redeploy / Rollback**
2. 롤백 후 `/actuator/health` `UP` 및 핵심 API 정상 응답 확인
3. 문제가 된 커밋은 `main`에서 되돌리거나(revert) 수정 후 재배포로 정리

> 원칙: **"먼저 멈춘 피를 막고(롤백), 원인은 안정화 후 분석한다."** 장애 중에 근본 원인 규명에 매달리지 않는다.

## 10. 장애 사후 기록 템플릿

장애 종료 후 아래 형식으로 `docs/incidents/YYYY-MM-DD-<슬러그>.md` 에 기록한다.

```markdown
## 장애 보고서 - YYYY-MM-DD

- 심각도: P1 / P2 / P3
- 발생 시각:
- 인지 시각:
- 복구 시각:
- 영향 범위: (영향받은 기능 / 사용자 범위)

### 타임라인
- HH:MM  증상 인지 (인지 경로: BetterStack 알림 / Grafana 알림 / Sentry / 사용자 제보)
- HH:MM  원인 파악
- HH:MM  조치 (롤백 / 수정 배포 / DB 복구)
- HH:MM  복구 확인

### 원인
- 근본 원인:
- 직접 트리거:

### 조치 내용
- 임시 조치:
- 영구 조치:

### 재발 방지
- [ ] (예: 테스트 보강, 알림 임계값 조정, 헬스체크/타임아웃 조정)
- [ ]
```

기록 시 원칙:
- 개인 책임 추궁이 아니라 **시스템/절차 개선** 관점으로 작성한다.
- 인지 시각과 복구 시각을 반드시 남겨 MTTR(평균 복구 시간)을 추적할 수 있게 한다.
